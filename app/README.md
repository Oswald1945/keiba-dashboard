# app/ — Webアプリ

既存の採点パイプラインを **そのままエンジンとして** 使うWebアプリです。
ルート直下の既存スクリプト・データには手を触れていません。

## 使い方

| やりたいこと | ダブルクリックするもの | 所要 |
|---|---|---|
| アプリを開く | `run_app.bat` | すぐ。ブラウザが自動で開きます |
| スマホから見る（同じWi-Fi内） | `run_app_phone.bat` | 表示されたアドレスをスマホで開く |
| 採点が変わっていないか確認する | `run_tests.bat` | 約5分 |
| 基準データを作り直す（採点変更を承認した後だけ） | `run_make_golden.bat` | 約5分 |

アプリは `http://127.0.0.1:8000` で動きます。**このPCの中だけ**で、インターネットには公開されません。
止めるときは黒い画面を閉じてください。

`run_app_phone.bat` は同じWi-Fi内の端末（スマホ）からも開けるようにするものです。
**パスワードはありません**ので、信頼できるネットワークでだけ使い、確認が終わったら閉じてください。
管理操作はこのPC（127.0.0.1）からのみ受け付けるため、スマホからは管理の実行はできません。

## いま出来ること（フェーズ1〜6）

画面を切り替えるボタンは **スマホでは画面下**、**PCでは画面上**にあります。

上部の「管理モード」を入れると「管理」「検証」が出ます。切っているときは
レースの閲覧とメモ馬・オッズの入力だけができます（**誤操作を防ぐための表示切替**で、
パスワードによる権限分離ではありません。それはフェーズ7で扱います）。

長い画面はすべて折り畳みにしてあり、**開いたときだけ中身を作る**ので軽く動きます。
開閉の状態はブラウザが覚えていて、次に開いたときも同じ状態になります。

**レース**
- 開催日ごとに折り畳み。開くと**会場ごとの列**（3場開催=3列／スマホ=1列）
- 検索は**レース名・クラス・馬名**に対応
- 「予想」「回顧」バッジを押すとその画面が直接開く
- オッズ手入力によるEV判定は、**予想ダッシュボード内の「期待値シミュレーター」「買い目提案」**
  を使う（アプリ側のEV判定タブは重複のため廃止）

**メモ馬**
- **50音の行ごとに折り畳み**（あ行106頭、か行81頭…）。行を開いたときだけ入力欄を作る
- 馬名ごとにまとめた一覧（同じ馬が別レースで登録されていればまとめて表示）
- メモ本文の編集（自動保存）
- 手動追加。同じ馬名が既にあれば既存の登録を見せて
  「上書き」「別レースとして新規登録」「馬名を修正して新規登録」から選べる
- アーカイブ（削除ではなく `app/data/memo_archived.json` へ移動。戻せます）

**管理**（①→⑦の順に押していけば終わります）

| 手順 | 内容 |
|---|---|
| ① データ更新 | JV-Link差分更新。実行前チェックリスト付き。RC=-303 は意味を表示 |
| ② レースを選ぶ | race.db から「予想できるレース」を一覧。新馬・未勝利は既定で選ばない |
| ③ 馬場を入れる | JRAの馬場情報から自動取得 → 確認・修正 → `baba_manual.json` |
| ④ 予想を作る | 採点 → 予想HTML。**公開はしない** |
| ⑤ 確認して公開 | ローカルで中身を見てから、選んだものだけ公開 |
| ⑥ 結果を取り込む | 速報の対象開催日を自動設定 → 取得 → 確定状況を表示 |
| ⑦ 回顧を作る／作り直す | 未作成分の生成と、速報で作った回顧の確定情報での作り直し |

SmartRC は rcode を race.db から自動で組み立てるので、手で調べる必要はありません。

**検証**（期間・馬場・クラスで絞り込み。過去1年／5年／10年／全期間／任意）

- 的中精度：軸複勝率・軸単勝率・上位3頭の着3内重複・順位相関。**1番人気を併記**して市場との差を出す。年／馬場／クラス／会場／芝ダ別の内訳
- 因子ごとの動向：16因子それぞれの単独複勝率・キャリブレーション（pts1位/2位/3位/残り）・順位相関・変動率。`スコア項目台帳.md` の診断表の自動再現
- 妙味：軸の単勝・複勝の回収率（**5年分を再計算なしで**算出）と、券種フォーメーション別の的中率・回収率

### 検証で気をつけていること

- **回収率の母数は「軸が出走した全レース」に固定。** `roi_rows.jsonl` の複勝配当は
  3着以内のときだけ記録されているため、素直に集計すると複勝回収率が143%という
  ありえない数字になる（結果を見てから買う計算）。正しくは78%前後。
  `test_validation.py` がこの取り違えを検出する。
- **5年データは採点ロジックの世代ごとに別ファイル。** 画面で切り替えられる。

  | 世代 | ファイル | 中身 |
  |---|---|---|
  | P3＋P4（現行） | `factor_rows_p4.jsonl` | 本番と同じ採点。これを選んで初めて現行モデルの成績になる |
  | P3のみ | `factor_rows_p3.jsonl` | コース適性ptsが現行と異なる |
  | ベースライン | `factor_rows.jsonl` | 上がりpts等が現行と異なる |

  新しい世代のファイルがあれば自動でそちらを既定にする。現行と違う世代を見ているときは
  警告色の注記が出る。採点ロジックを変えたら、管理タブ⑧で作り直す
  （実測 約2.8秒／レース＝5年で約12〜13時間・再開可能・既存ファイルは上書きしない）。
- 新馬・未勝利は精度検証外（CLAUDE.md）。既定で除外。
- 順位相関は `scipy` を使わず `numpy` 相当の自前計算（依存を増やさないため。
  なお `validate_accuracy.py` は scipy 未導入のためこのPCでは動きません）。

まだ出来ないこと: インターネット公開と認証（フェーズ7）。

## 見た目について

アプリも予想・回顧ダッシュボードも、**JRA公式サイトから採取した色とフォント**に揃えてあります。

| | 値 |
|---|---|
| 緑（主色） | `#00674A` |
| 下地 | `#DDE8E2` ／ カードは白 |
| 文字 | `#2B2B2B` ／ 補助 `#5C6B63` |
| フォント | `"Hiragino Sans", メイリオ, Meiryo, ...`（JRAと同じ指定） |

**枠色（1枠白・2枠黒…）と積み上げチャートの因子色は変えていません。**

色やフォントを変えるときは、`app/frontend/src/styles.css` と
`build_dashboard_v3.py` / `build_review.py` の**両方**を合わせて直してください。
片方だけ直すと、アプリの外枠とダッシュボードの中身がちぐはぐになります。
なお、**生成済みのHTMLは作り直すまで古い見た目のまま**です。

### 設計の要点

- **採点ロジックはアプリ側に一切書き写していない。**
  `runner.py` が `run_new.py` と同じコマンドラインで既存スクリプトを起動するだけ。
- **EV計算の移植版 `evCore.js` は画面からは使っていないが、残してある。**
  `app/tests/ev_parity.mjs` が「ダッシュボードに埋め込まれたJS」と「移植版」を突き合わせるので、
  ダッシュボードのJSをうっかり壊したときに気づける。EV判定の画面は廃止したが、
  この見張り役としての価値があるため削除していない。
- **書き込むのは `app/data/` と `memo_horses.json` だけ。**
  `memo_horses.json` は項目構成も書式（`ensure_ascii=False, indent=2`）も既存のまま。
  `run_new.py` の自動登録と `build_dashboard_v3.py` の読み取りに影響しない。

### メモ馬の同時更新について（重要）

`run_new.py` は回顧を作るたびに `memo_horses.json` を**丸ごと書き換え**ます。
アプリが画面の内容をそのまま全件保存すると、その間に自動登録されたメモが消えます。
そこで2段構えにしてあります。

1. 保存は必ず「最新を読み直して**1件だけ差し替え**」。全件上書きはしない。
2. 画面を開いたときとファイルの中身が変わっていたら**保存を拒否**（409）し、
   「読み直してください」と表示する。黙って上書きしない。

上書き前の内容は `_archive/app_backups/` に日時付きで退避されます。

### EVロジックを更新するとき（将来の期待値検証）

1. `evCore.js` の `EV_CORE_VERSION` を上げる。
2. パリティテストは「既存 pred.html と一致すること」を見ているので、**必ず落ちる**。
   これは正常。既存 `build_dashboard_v3.py` 側も同じ変更を入れるか、
   パリティ対象から外すかを決めてから進める（勝手に外さない）。
3. 保存済みオッズには入力時の `ev_core_version` が残っているので、
   「どの版のロジックで見ていた判断か」を後から区別できる。

## 回帰テストについて

`app/tests/golden/` に100レース分の入力CSVと「今のコードの出力」が保存してあります。
`run_tests.bat` は同じ入力を今のコードで作り直し、次の全部が一致するかを見ます。

1. `horses_data.json`（16因子pts・総合スコア・順位予想・地方フラグ など全項目）
2. `scores.csv`
3. 予想／回顧ダッシュボードHTML（ハッシュ）
4. EV_DATA（アプリのEV APIと既存HTML埋め込みの一致）
5. EV計算そのもの（勝率・EV・採算オッズ・買い目軸・購入推奨・券種ごとの点数と的中率）

不一致が出たら、どのレースのどの馬のどの項目が「基準→今回」でどう変わったかが表示されます。

**基準を作り直してよいのは、採点ロジックの変更を承認した後だけです。**
テストが落ちたからといって `run_make_golden.bat` を実行すると、変更を検知できなくなります。

### 100レースの内訳（端ケースを必ず含めています）

- 地方実績のみの馬を含むレース
- 馬場が良以外
- スコア1位が人気薄（＝勝率cap で買い目軸が動く）
- 坂路・ウッドが欠けているレース
- レース結果あり（回顧まで検証できる）
- ダート

### テストが「スキップ」になる場合

コードの問題ではなく、**基準を作ったときの前提が変わった**ときです。理由が表示されます。

- `input/done/` のレース結果CSVが動いた → トラックバイアス実測の元データが変わるため
- `memo_horses.json` のうちそのレースに効く分が変わった → HTMLのメモ馬バッジが変わるため
  （この場合も採点数値の比較は行われます）
